# FuncType 科別代碼補充別名表 — 待確認清單

**狀態**：待人工確認，尚未套用至 `app/services/medical/department_matcher.py`
**來源**：https://www.ghd.tw/cdm-fhir/CodeSystem-FuncType.html（49 個代碼）
**日期**：2026-08-27

## 摘要

把 FuncType 的 49 個科別代碼跟 `CANONICAL_DEPARTMENTS`（43 個值）對過：

| 分類 | 數量 |
|---|---|
| 兩邊字面完全相同 | 24 |
| FuncType 有、`DEPARTMENT_ALIASES` 已解得出 | 12 |
| FuncType 有、**別名表解不出** | **13** ← 本文件處理 |
| 資料庫有、FuncType 沒有 | 19 |

最後一列說明 **FuncType 不是超集，不能取代 `CANONICAL_DEPARTMENTS`**：牙科次專科（牙髓病科、齒顎矯正科、贋復補綴牙科、兒童牙科、牙周病科、家庭牙醫科、特殊需求者口腔醫學科）、中醫一般科、西醫一般科、一般精神科、成癮防治科等 19 個資料庫實際存在的值，FuncType 都沒有。本次僅取其補充別名。

中間那 12 個「已解得出」的等於反向驗證了現有別名表的次專科映射是正確的（消化內科→內科、胸腔外科→外科、腎臟內科→內科…），無須改動。

## 先修一個現存的錯誤映射

`口腔顏面外科` 目前會被**靜默對應到錯的科別**：

```
輸入：附近有沒有口腔顏面外科
extract_department_intent() →
    canonical = 外科      ← 錯，應為 口腔顎面外科
    requested = 外科
    is_alias  = False     ← 因此「別名轉換」的誠實揭露不會觸發
傳給工具的 department = '外科'，回覆對使用者說「外科」
```

成因：官方代碼寫「顏」面，資料庫寫「顎」面。字面比對失敗後，`extract_department_intent()` 的子字串掃描退而抓到「外科」，於是產出一個看起來正常、實際上丟失了資訊的答案。因為 `canonical == requested`，`is_alias` 為 False，`department_matcher` 原本設計來告知使用者「你說的 X 在健保資料中歸類於 Y」的機制也不會啟動。

這是最難察覺的一類失效：不是「系統看不懂」，是「系統很有自信地答錯」。

**同一機制的次要影響**：`心臟血管內科`、`心臟血管外科`、`消化外科`、`直腸外科`、`新生兒科`、`脊椎骨科` 這 6 個在整句掃描下**答案剛好是對的**（都經由「內科」「外科」「兒科」「骨科」子字串命中），但 `requested` 同樣被覆寫成子字串，別名揭露一樣被抑制 —— 使用者說「心臟血管內科」，回覆只會說「內科」，不會說明兩者的對應關係。

## 收錄的成本與效益（釐清預期）

查詢路徑是 `_resolve_department_with_fallback()`：先 `resolve_department()` 查表，**表查不到才走 LLM 兜底**（有快取，同一新詞一輩子一次）。

因此「不收進表」的實際後果不是「查不到」，而是：

1. 每個新說法付一次 LLM 呼叫；
2. 答案由模型決定，不確定、不可單元測試逐條斷言；
3. 整句掃描路徑可能先搶著給出上述的錯誤答案，根本輪不到 LLM。

收進表的效益是把這些變成 0 延遲、確定性、可測試。**唯一功能性修正是 `口腔顏面外科`**，其餘是穩定性與誠實揭露的改善。

| A5 | 直腸外科 | BA | `外科` | 表中已有 大腸直腸外科／直腸科／大腸直腸肛門科 | — |

| A9 | 胸腔暨重症加護 | AJ | `內科` | 內科次專科。民眾不會掛號此科，收錄僅為避免落到 LLM 兜底 | 重症加護科 |

**A8 的界線**：只收「結核科」「結核病科」這類**科別說法**，**不收「肺結核」**。後者是病名，收了就違反 `department_matcher` 模組註解訂下的「不從症狀／病名推科別」原則（該原則目前唯一例外是「痔瘡」，且已於程式註解說明為何不構成破例）。

**A7 的界線**：不建議收「脊椎外科」。脊椎手術由骨科與神經外科共同承擔，這個說法本身就有歧義，硬定一邊等於做了不該由別名表做的判斷。現有的「脊椎」→骨科 已足以覆蓋整句掃描。

## B. 已確認（2 條）

### B1. 老人醫學科 (AK) → `家醫科` ✅ 已確認（2026-08-27）

台灣老年醫學次專科由內科或家醫科醫師取得，兩條路都成立。

- **選 `家醫科`（我的建議）**：老年醫學門診的本質是整合式初級照護與多重用藥整合，與家醫科的職責定義最貼近；且診所層級的家醫科密度遠高於內科老年醫學次專科，使用者實際找得到院所的機率較高。
- **選 `內科`**：醫學中心的高齡醫學中心多隸屬內科系，若使用者想找的是大型醫院的高齡整合門診，內科較準。

一併收：老年醫學科、高齡醫學科、老人科、老年科

### B2. 疼痛科 (DA) → `麻醉科` ✅ 已確認（2026-08-27）

資料庫沒有「疼痛科」這個值，但 FuncType 有此正式代碼（我先前說它是「院所特有分科」是錯的）。

- **收 → `麻醉科`（我的建議）**：疼痛科在台灣是麻醉科次專科，疼痛門診由麻醉科醫師執業，醫理鏈正確。風險是院所登記「麻醉科」不代表有開疼痛門診，使用者可能撲空 —— 但因 `is_alias` 為 True，回覆會誠實說明「疼痛科在健保資料中歸類於麻醉科」，使用者能自行判斷是否先去電確認。附帶效果：「疼痛門診」會被 `_INTENT_SUFFIX_RE` 剝掉「門診」後自動命中，不必另收。
- **不收**：但這保護不了什麼 —— LLM 兜底的 enum 裡就有麻醉科，多半仍會答麻醉科，只是多付一次呼叫且答案不確定。

## C. 建議不收（2 條）

### C1. 潛醫科 (AI)

潛水醫學／高壓氧。對應不明確：高壓氧中心可能設於急診醫學科、職業醫學科或整形外科（傷口治療）底下，沒有單一正確答案。流量趨近於零，猜錯的成本大於收錄的效益。維持現況（落到 LLM 兜底或回「無法解析」）。

### C2. 居家照護 (EA)

**這不是科別，是服務類型。** 收進科別別名表會讓「我想找居家照護」被導向某一科的門診，答非所問。居家醫療整合照護是另一套資源體系（申請管道、給付條件都不同），應另案處理，不應混入 `DEPARTMENT_ALIASES`。

## 附帶發現（已查證，非問題）

`db.medicalFacilities.aggregate([{$unwind:"$departments"},{$group:{_id:"$departments",count:{$sum:1}}}])`
實際回傳 **44** 個 distinct 值（2026-08-27 查）。與 `CANONICAL_DEPARTMENTS` 比對：

- CANONICAL 有、DB 沒有：**0 個**（清單無冗餘，沒有查了必定 0 筆的科別）
- DB 有、CANONICAL 沒有：**1 個** —— `耳鼻喉科(耳鼻喉頭頸外科)`（4 筆）

那 1 個不需要補：`build_department_query()` 用的是 regex 而非精確比對，已驗證
`耳鼻喉科` 的 regex 會命中 `耳鼻喉科(耳鼻喉頭頸外科)`。

**結論**：`CANONICAL_DEPARTMENTS` 的 43 個值是正確且完整的，
[department_matcher.py:20](../app/services/medical/department_matcher.py#L20) 註解寫的
「55 個 distinct 值」單純是過時數字，改成 44 即可。

## 另一個發現：家醫科／家庭醫學科是兩個獨立值

DB 同時存在 `家醫科`（1,633 筆）與 `家庭醫學科`（275 筆），兩者都在
`CANONICAL_DEPARTMENTS` 內。但 `build_department_query()` 以
`re.escape(canonical)` 產生 regex，**`家醫科` 的 regex 不會命中 `家庭醫學科`**
（反之亦然）。

因此使用者說「家醫科」時會漏掉 275 筆院所，說「家庭醫學科」時會漏掉 1,633 筆。
兩者在醫療上是同一科，這個切分沒有意義。

本次 B1 把「老人醫學科」對應到 `家醫科`，同樣受此影響。

**建議另案處理**（不在本清單範圍）：讓部分 canonical 值可對應到一組 regex 而非
單一字串，或在資料層正規化。需要先確認會不會影響其他科別的查詢語意。
