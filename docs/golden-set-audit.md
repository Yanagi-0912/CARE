## 為什麼要做這件事

原本只是要補 `expected_title_substrings`（不隨切片方式失效的穩定標籤）。
在推導過程中發現標籤本身大面積不可信，因此停下來改做全面稽核。

觸發點：`golden.jsonl` 的 `notes` 欄位。

```json
"notes": "tighten: gold_rank=17 kw=3 url=pid=16550"
```

`scripts/rag_tighten_golden.py` 是**拿當時檢索結果的第 N 名當標準答案**。
若當時檢索本身不準，它就把雜訊封存成了「正確答案」——標籤生成過程是循環的。

## 兩個獨立的發現

### 發現一：標籤腐化已經在發生

34 題中有 **7 題**（21%）的 `expected_content_substrings` 已經比對不到庫中任何 chunk：
`kb-002`、`kb-006`、`kb-012`、`kb-013`、`kb-026`、`kb-027`、`kb-029`。

這 7 題的文章**都還在庫裡**（各有 2–6 個 chunk），只是那段被複製下來的文字
已經因為 chunk 邊界位移而對不上了。**沒有人改過切片程式碼** —— 光是每日 ETL
的正常運作就足以造成這個結果，時間跨度約 8 天。

這才是 `hit_rate` 只有 0.44 的主因，而且與檢索品質無關。

**題庫問的是健康百科式問題**：「血壓多少算高？」「疫苗常見副作用有哪些？」

## 建議順序

1. 先處理 🔴 那 7 題（標籤明確錯誤，改動風險低）
2. 決定 🟠 那 12 題的處理方式（需要你拍板）
3. 兩者完成後，才補 `expected_title_substrings` 穩定標籤 ——
   **順序不能顛倒**，否則等於把錯誤標籤變得更耐久
4. 重跑 eval 取得新基準。這個數字才第一次真正代表檢索品質

## 方法與限制

- 候選文章來自對全庫 1,641 個相異標題的關鍵詞比對，**不使用檢索排名**，
  以避免重蹈 `rag_tighten_golden.py` 的循環標註問題
- 主題相關性判斷依據標題與首段內容，**未逐篇通讀全文**
- 🔴 區的判斷信心較高（現行標籤與問題主題明顯無關，且候選標題直接回答問題）
- 🟠 區的「庫中沒有答案」是基於關鍵詞涵蓋率的推論，可能漏掉標題未含關鍵詞
  但內容相關的文章

題庫結構：`kb` 22 題 / `web` 13 題 / `refuse` 3 題（原 34 / 1 / 3）

### 新基準（RRF 混合排序，`--rank-mode vector`）

| 指標 | 稽核前（34 題） | 稽核後（22 題） |
| --- | --- | --- |
| hit_rate@5 | 0.441 | **0.818** |
| mean_mrr | 0.241 | **0.505** |
| mean_ndcg@5 | 0.291 | **0.575** |

**這兩欄不可直接相比** —— 題目集不同，移除無解題目本身就會抬高比率。
差別在於：右欄量的是「KB 確實能回答的題目上，檢索有沒有找到答案」，
左欄量的是「與一份部分錯誤標籤集的吻合度」。

### 剩餘 4 題 miss 是真實的排序失誤，不是標籤問題

已逐題以 `rag_query_cli.py` 查證：期望文章**都在 40 筆 wide-retrieve 候選內**，
只是精排沒有把它們推進 top-5。

| id | 問題 | 期望文章在候選中的名次 |
| --- | --- | --- |
| kb-014 | 中風前兆有哪些？ | 第 7、13、37 名 |
| kb-026 | 一週要運動多久才有效？ | 第 14、18 名 |

**召回沒問題，問題在排序。** 這正是 reranker 該解決的事。

### Cohere 數字待補

最後一輪 Cohere 執行時每次呼叫都收到 `429 Too Many Requests`，
`CohereReranker` 依設計 fail-open 降級為 `VectorScoreReranker`，
因此該輪數字實為 RRF 而非 Cohere（已與 `--rank-mode vector` 交叉比對確認完全相同）。

套用 kb-018 標籤前的 Cohere 數字為 0.773 / 0.459 / 0.533，
低於同條件的 RRF —— 與先前 `ndcg@5_delta −0.186` 的發現方向一致。
待配額恢復後應重跑 `--compare-rerank` 取得同標籤條件下的乾淨對照。

**附帶觀察**：這次 429 意外驗證了 `CohereReranker` 的 fail-open 設計 ——
在外部 API 完全不可用的情況下 eval 仍完整跑完，沒有中斷。

### Cohere vs RRF —— 乾淨對照（2026-08-09，更換可用金鑰後補測）

先前記錄的「Cohere 弄壞的題數是修好的 6.5 倍」「Cohere 正在明顯降低檢索品質」

修正後的判斷：**在這份語料上，Cohere 精排與 RRF 混合排序的品質差異接近雜訊等級**，
