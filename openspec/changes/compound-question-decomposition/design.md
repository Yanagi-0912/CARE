## Context

評測題組：26 題繁中（8 組 single_a／single_b／compound，加 2 題「單一問題多條件」控制題 C01、C02），題材取自 8 篇健康新聞，題目自行撰寫、不含新聞原文、`gold_answer` 皆為 null——**以下數字全是非臨床指標（答不答得出、子問題保不保得住、延遲），不是醫療正確率**。

所有實驗在線上 care-vm 以一次性 Job 執行，映像與線上相同（`276-ccaa8ef`），模型設定與 CARE-infra `values.yaml` 一致（agent／拆題 `gemini-3.8-flash`、生成 `gemini-3.5-flash-lite`、hybrid＋Cohere＋CRAG），Web Fallback 一律關閉以量知識庫本身。除 baseline 外每個條件跑 3 輪取多數。

「參考子問題」＝單獨問時答得出的 8 個子問題（T01b、T02a、T02b、T05a、T05b、T06a、T06b、T08b）。

## Goals / Non-Goals

**Goals：** 複合問題中知識庫答得出的部分照常回答；答不出的部分明說；單一問題與非複合訊息行為完全不變；開關關閉時零影響。

**Non-Goals：** 提高醫療正確率、放寬 CRAG、補知識庫內容、非 zh-TW 語言、非問號連接的複合訊息。

## Decisions

### 決策 1：拆題判斷放在 RAG 層，不放在 Agent 的工具參數

實驗 B 讓 `get_rag_answer` 多一個選填 `sub_questions`，由既有那次 agent 工具選擇順便填：

- 過度拆題 0/54，但複合題拆題召回只有 **7/24（29%）**，且每輪不一致——agent 偏好把兩題揉成一串關鍵字查詢。
- 本地 RAG 分流捷徑（`AgentNodes._local_rag_shortcut`）命中時直接以原句呼叫 `get_rag_answer`、**不經 LLM**；T01／T02／T03 三題複合題每輪都走捷徑，工具參數方案對它們完全無效。

實驗 C 改在 RAG 層：規則閘（問號 ≥ 2）＋獨立拆題 LLM（吃原始訊息）：

| | 複合題命中 | 單題過度拆 | 控制題過度拆 |
|---|---|---|---|
| 只用拆題器 | 22/24 | 3/48（全是「飲食和活動要注意什麼」被拆成兩題） | 0/6 |
| 規則閘＋拆題器 | **21/24** | **0/48** | **0/6** |

規則閘擋下了拆題器唯一的過度拆題；唯一漏掉的是以「；」連接兩問的 T08（只有一個問號）。捷徑題 T01–T03 也都涵蓋。

**替代方案（否決）**：強化 agent prompt——即使召回拉高，捷徑路徑仍然繞過。

### 決策 2：拆題器吃原始使用者訊息，不吃 agent 寫的 query

agent 會把問題改寫成關鍵字串，實測會讓原本查得到的題目查不到（T05_single_a：關鍵字串 1 輪查無、原句 3/3 查得到；C02「抗生素 咖啡 交互作用」3/3 查無、原句查得到）。拆題需要完整語意，因此由 `Agent.invoke` 以 ContextVar 保存本輪原文。

**只有 `get_rag_answer` 會傳原文**：藥單問答（`medication_question_service`）送進 RAG 的查詢附加了登記藥名、查核（`dependencies._claim_...`）送的是主張本身；若 RAG 服務自行讀 ContextVar，這些路徑會被拆題改寫而遺失附加內容。因此採明確參數 `answer(query, *, original_message=None)`，呼叫端不傳就等於關閉。

### 決策 3：每個子問題只用自己的候選，不做原句那一路檢索

Ammann et al. 2025 建議原句與子問題一起檢索、合併後再精排。實驗 A 在 CARE 知識庫上得到相反結果：

| 每個子問題精排的候選 | 參考子問題保住 |
|---|---|
| 三路（原句＋各子問題）合併的整池 | 7/8 |
| 自己的候選 ∪ 原句的候選 | 7/8 |
| **只用自己的候選** | **8/8** |

失效案例 T05 Q1（便祕原因與警訊）：原句那一路撈到一篇 Cofacts 謠言文，精排 0.662 排第一，CRAG 9/9 判 `ambiguous`；只用自己的候選時 3/3 `correct`。推測原因：知識庫混有大量 Cofacts／TFC 謠言文，而長輩的原句又長又口語，容易把它們撈進來。

### 決策 4：子問題只保留「會改變答案」的條件，檢索另用核心主題

實驗 C 的拆題器被要求「補上主詞與必要情境」，結果把原題所有條件帶進每個子問題（條件擴散）：T06「同時有糖尿病和腎臟病」進了兩題，兩題都變成知識庫沒有的「多條件」查詢。

實驗 C2（只差這一條規則的消融）：

| | 保留全部相關條件 | 只留拿掉會改變答案的條件 |
|---|---|---|
| 閘門內複合題答出（3 輪平均） | 3.3/8 | **4.3/8** |

進步來自 T03、T07（子問題不再夾帶另一個子問題的病況）與 T05（多拆出「就醫警訊」子問題）。

實驗 C3 再把寫法分成兩種：`retrieval_query`（檢索＋精排，只留核心主題）與 `question`（CRAG＋生成，保留會改變答案的條件）。端到端與 C2 打平（答出 4.7 vs 5.0/8，雜訊內），但檢索明顯變好（T06 Q1 精排 0.63→0.86，撈到腎友鉀鈉磷衛教），瓶頸移到 CRAG——它用帶全部條件的 `question` 評分，判的是「這些文件能不能回答這位使用者」。T01 Q2 是直接證據：三輪檢索結果完全相同（0.75），`question` 帶「三酸甘油脂偏高」→ `ambiguous`，不帶 → `correct`。

**本變更採 C3 的兩種寫法**：檢索端的改善是實的，而 CRAG 用完整條件評分是刻意保留的安全行為（見決策 5）。

### 決策 5：CRAG 維持嚴格，不做「部分支持」

實驗 C4／C5 試過兩層判定（完整條件不過、核心查詢通過 → 部分支持，生成首句說明適用範圍）：閘門內答出 13→15/21，但 7 個部分支持答案中 3 個有問題，其中 T06「慢性腎臟病患者應遵守低蛋白飲食」把「依分期而定」講成人人適用，正好答反使用者問的「是不是每個人都一樣」。放行只部分適用的醫療內容需要臨床審核，**不在本變更範圍**。

嚴格 CRAG 的意義：拆題路徑放行的每一段，都通過了與現行相同標準的分級；本變更只讓「答得出的那部分」不再被答不出的部分拖垮，不放寬任何一段的標準。

### 決策 6：生成只給通過的子問題，不給原始整句

C4 讓生成看得到原始整句，出現兩種失效：

- **前後矛盾**：模型替未通過的子問題也寫了一段，程式又補「查無資料」（C4 T06 r2）。
- **CRAG 放行、生成拒答**：子問題已判 `correct`，模型看到原句裡還有它答不了的部分，寫出拒答標記，整題變成 MODEL_REFUSE（C3 2 次、C5 對照臂 1 次）。

C5 改成只列通過的子問題後：含未通過子問題的 10 則答案人工讀過 0 則矛盾，MODEL_REFUSE 0 次（T04 3/3 正常答出）。子問題本身已保留會改變答案的條件，不給原句不會遺失這些資訊；代價是少了「您的父親」這類稱呼。

### 決策 7：未通過的子問題由程式補固定句

實驗 A 發現模型被要求「對查無資料的子問題寫一句說明」時，會寫成拒答標記而讓整題被判拒答。改由程式在生成後補固定句（i18n key `rag.compound_unsupported`），句中不含引用標記，確保這句話不會被掛上來源。

### 決策 8：全部不通過或任何一步失敗時退回現行流程

- 拆題器判單一問題、少於 2 個子問題、呼叫或解析失敗 → 現行流程。
- 所有子問題都未通過 CRAG → 現行流程（含 Web Fallback）。
- CRAG 分級例外、生成仍只寫拒答標記 → 現行流程。

理由：拆題路徑只在「至少一個子問題以知識庫答得出」時接手，其餘情況與現況完全相同，不會比現況差。

**已知取捨**：部分子問題通過時，未通過的子問題回固定句，而不是走 Web Fallback。現況下整題 CRAG 不過會走網搜，網搜也可能答出那一半；本變更在「部分通過」時優先給出有知識庫來源的部分。逐子問題網搜留待後續評估。

### 決策 9：只處理 zh-TW

拆題 prompt、規則閘（全形問號）與全部實驗都只涵蓋繁中。非 zh-TW 請求一律走現行流程。

## Risks / Trade-offs

- **樣本小**：8 題複合題，差 1 題就是 12.5 個百分點；題組人工撰寫、標點工整，真實 LINE 訊息的閘門命中率未知 → 開關預設關閉，先在 dev 觀察日誌中的 `rag_compound` 路徑比例。
- **誤刪會改變答案的條件**：C2 中「天熱頭暈是否缺水」3/3 刪掉「心臟或腎臟疾病」。該子問題仍需通過 CRAG，但答案可能少了「有這些病的人頭暈要另外留意」的提醒 → 列為後續變更。
- **延遲**：compound 訊息多一次拆題呼叫（p50 約 1.5–2 秒，p95 約 3 秒），序列在檢索之前。
- **成本**：每個子問題各一次檢索、Cohere 精排、CRAG 分級；Cohere Trial key 有速率限制，429 時既有機制降級為 RRF 排序。
- **生成品質**（過度概括、偶發夾雜外文）是生成模型的既有問題，現行流程同樣存在，不因本變更惡化，也不由本變更處理。

## Migration Plan

1. 合併後開關維持 `false`，線上行為不變。
2. dev 環境設 `RAG_COMPOUND_DECOMPOSE_ENABLED=true`，觀察 `rag_compound` 日誌（子問題數、通過數、退回原因）與延遲。
3. 回滾：開關改回 `false` 重新部署即可，無資料遷移。
