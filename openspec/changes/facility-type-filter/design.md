## Goals / Non-Goals

**Goals**

- 使用者能區分「大醫院」與「診所」，不再被 97% 的診所淹沒。
- 類型與科別可疊加，支援「大醫院的腸胃科」。
- 省略類型時行為完全不變（向後相容）。

**Non-Goals**

- 不補藥局資料（僅 116 家）。本 change 只確保查無藥局時給出誠實、可行動的訊息。
- 不將「病理中心」（13 家）納入任何使用者可選類型 —— 民眾不會直接前往。
- 不做營業中篩選（另案）。

## Decisions

### 決策 1：擴充現有工具的選填參數，不新增第三個工具

三個候選：

| 方案 | 評估 |
|---|---|
| (a) 新增 `find_nearby_facilities_by_type` | ✗ 模型需在三個高度重疊的工具間選擇，誤選率上升；且**無法表達「大醫院的腸胃科」** |
| (b) 兩個現有工具各加選填 `facility_type`（**採用**）| ✓ 類型是過濾維度而非搜尋模式；兩維度天然疊加；省略時完全相容 |
| (c) 合併成單一工具、科別與類型皆選填 | ✗ 改動面過大，且會破壞既有 prompt 規則與 16 項跨輪測試 |

類型與搜尋模式是不同層次的概念：「要不要限定科別」決定走哪個工具，
「要醫院還是診所」只是加一個過濾條件。方案 (b) 讓這個層次差異在介面上保持明確。

### 決策 2：分類表只含醫院／診所／藥局，不含牙醫與中醫

「牙醫」「中醫」已存在於 `DEPARTMENT_ALIASES`（→ 牙科、中醫一般科）。若同時作為類型分類，
同一個詞會映射到兩個維度並以 `$and` 疊加，反而**縮小**結果集。

實測可證明科別維度更適合這兩個詞：

- `departments` 含「中醫一般科」：**3,517** 筆
- `type` 為中醫類（中醫一般診所＋中醫診所＋中醫專科診所＋中醫醫院）：**3,496** 筆

差額代表有些**非中醫類型的院所設有中醫科**（如綜合醫院的中醫部）。使用者問「附近有中醫嗎」
時，把醫院的中醫部排除掉並非其本意。因此這兩個詞歸科別維度，類型維度不重複收錄。

使用者若說「牙醫診所」，兩個維度各自命中（科別牙科 × 類型診所），疊加結果正確。

### 決策 3：類型用 `$in` 精確比對，不用 regex

與科別的策略**刻意不同**，原因是資料特性不同：

- `departments` 有髒資料（整串塞在單一元素），且需要「內科」命中含內科的長字串 → 必須 regex。
- `type` 乾淨且值互為子字串：「醫院」是「綜合醫院」「中醫醫院」「精神科醫院」的子字串。
  若用 regex `醫院`，「中醫醫院」會被算進「醫院」類（可接受），
  但反過來若使用者要「診所」而用 regex `診所`，會同時命中 10 種診所值（正確）——
  問題在「醫院」的 regex 無法排除掉未來新增的值，且無法表達「醫院但不含中醫醫院」這類需求。

`$in` 以明確的值集合表述分類，語意精確且可測試（`type` 只有 17 個值，全部列舉可行）。
代價是資料庫新增 `type` 值時分類表需同步 —— 以守門測試因應（見決策 4）。

### 決策 4：以守門測試防止分類表與資料庫脫節

比照 `test_all_alias_targets_exist_in_database`，新增測試斷言分類表中的每個 `type` 值
都確實存在於 `CANONICAL_FACILITY_TYPES`（由資料庫 distinct 值維護的常數）。
資料庫新增類型值時測試會失敗，迫使人工決定歸類。

### 決策 5：查詢條件以 `$and` 組合

`_search_tiered()` 目前接受單一 `query` dict。科別與類型併存時：

```python
filters = [f for f in (department_query, type_query) if f]
query = filters[0] if len(filters) == 1 else {"$and": filters}
```

僅一個條件時不包 `$and`，保持既有測試斷言（`{"departments": {...}}`）不變。

## Risks / Trade-offs

| 風險 | 影響 | 緩解 |
|---|---|---|
| 兩維度疊加後結果過少 | 「大醫院的皮膚科」在偏鄉可能 0 筆 | 已有 5→50 公里階梯與 `satisfied=False` 部分結果機制承接 |
| 藥局僅 116 家 | 使用者搜尋藥局幾乎必然失敗 | 專屬文案說明資料有限並建議改用名稱查詢；資料補齊另案 |
| 分類表與 DB 脫節 | 新 `type` 值被靜默漏掉 | 決策 4 的守門測試 |
| 模型未帶 `facility_type` | 退化為不分類型（現狀行為）| 可接受；`nodes.py` 的強制注入路徑提供保底 |
| 「醫院」一詞的歧義 | 使用者說「醫院」可能泛指「醫療院所」 | 需在 prompt 明確：泛稱「醫院」不套類型，僅「大醫院／大型醫院／住院」等明確語彙才套 |

## Migration Plan

無資料庫遷移、無新增索引。`facility_type` 為選填參數，省略時行為與現狀完全一致，
既有 804 項測試不需修改。

## Open Questions

- 「病理中心」（13 家）與 `type` 為「一般診所(醫務室)」（3,076 家，多為機關內部醫務室，
  可能不對外開放）是否應預設排除於一般搜尋之外？
- 使用者說「醫院」時的預設解釋為何？決策上傾向「不套類型」（視為泛稱醫療院所），
  但這會讓「附近有醫院嗎」仍然回傳診所 —— 需要在實作時以實際對話樣本再確認。
