# 設計：每日醫療消息卡與認同分享

## 決策 1：兩層選材，且兩層在版面上必須可分辨

每日必定推一則。命中使用者用藥的警訊為 **Tier 1**，沒有命中時退回一般衛教時事為 **Tier 2**。

「每天都要有東西推」這個約束有代價，必須先講明：官方來源不是每天都有值得看的新消息，
強制填滿會逼系統降低內容品質下限。CARE-data 已經踩過同一個坑——`ADMIN_NOISE_KEYWORDS`
存在的理由，正是食藥署新聞稿 feed 裡有 18%（706 篇中 129 篇，該專案實測）是法規預告、
研討會、表揚典禮這類沒有衛教價值的行政公告。

更要緊的是通知疲勞：大多數日子推的是泛泛時事，使用者會學會忽略這張卡，然後真正命中他
用藥的那天，那則高價值警訊會跟著被一起忽略——用低價值內容稀釋掉高價值內容。

因此**兩層 SHALL 使用不同的卡片版面與標題**，而不是同一張卡換內容：

- Tier 1：醒目標示「與您正在服用的藥有關」，附藥名。
- Tier 2：低調標示「今日醫療小知識」，不提任何藥名。

這條是承重的。少了它，Tier 1 的價值會被 Tier 2 稀釋，而稀釋的過程沒有任何訊號——不會
報錯、不會有 log，只會表現為「使用者不再點卡片」，而那時已經來不及。

**證據強度**：通知疲勞是有文獻基礎的一般現象，但「兩種版面能否讓長輩分辨」在本專案
**未經量測**，屬待驗證假設。列為 Open Question 1。

## 決策 2：索引與推播分離，快取鍵是藥名而非使用者

即時搜尋 + 抓取 + LLM 判定的量級是十幾秒，不能放在推播的同步路徑上。有三種做法：

| 方案 | 成本成長 | 問題 |
| --- | --- | --- |
| 按「人」預算 | O(使用者數) | 同一個藥被 N 人服用就搜 N 次 |
| **按「藥」快取（採用）** | O(不重複藥數) | 需要一支獨立排程 |
| 推播時即時算 | O(使用者數 × 每日) | 每日燒搜尋與 LLM 額度，且無法容忍上游逾時 |

關鍵觀察：**因為來源鎖死官方域，同一個藥名搜出來的結果與「誰在吃」完全無關**。個人化
只發生在最後一步「這位使用者吃哪些藥 → 撈對應的快取」。

分離還有第二個理由，比成本更重要：**政府站台逾時是常態**。合在一起時搜尋失敗會讓整輪
推播停擺；分離後索引失敗只是「今天沒有新內容」，推播照常拿昨天的索引跑。這與本專案把
`drug_catalog.json` 提交進 repo、不讓部署依賴政府站台活著，是同一個判斷。

兩支排程器 SHALL 各自登記 `scheduler_heartbeat`，理由同 `medication_scheduler`：合併登記
會讓其中一支停擺被另一支的心跳掩蓋。

## 決策 3：來源限定官方域，SHALL NOT 做開放網路搜尋

沿用既有的 `RAG_WEB_SEARCH_SITE_FILTER`（預設 `site:gov.tw`）與 `whitelist.is_allowed_url`，
SHALL NOT 為本功能新增搜尋路徑或放寬白名單。

理由不是保守，是這個功能的錯誤方向與 RAG 問答不同：

1. **健康類關鍵字的自然搜尋結果商業污染最重。** `whitelist.py` 的收錄判準第三條就是
   「無商業銷售動機」。「某某藥 副作用」的搜尋結果裡，賣保健品與診所導流的文案正是設計
   來讓人停藥改買別的。
2. **主動推播比被動回答責任重得多。** 使用者發問時拿到答案是他發起的；系統主動推
   「你在吃的藥出問題了」沒有脈絡，對高齡使用者最可能的反應是**自行停藥**，而停藥的
   傷害是實質且立即的。

已知覆蓋缺口：食藥署的 `DataAction` 新聞稿 feed 雖已入庫，但該端點**結構上不提供文章
網址**（CARE-data 已記錄此限制），因此該來源的文章無法作為消息卡——消息卡必須有可點的
來源連結，分享給家人的卡片尤其，那是收件人唯一能自行查證的東西。

## 決策 4：判定失敗時 fail closed，與 rag-crag 刻意相反

`rag-crag` spec 明文規定 grader 或改寫呼叫失敗時 SHALL 降級為「照常以現有文件生成」。
本能力的對應行為**相反**：判定失敗、逾時、結構化輸出不合法時 SHALL NOT 推 Tier 1，
降級為 Tier 2 或當日不推。

不對稱的理由：CRAG 那條路上使用者正在等答案，沒答案比不完美的答案糟；這條路上沒有人在
等，**沒推遠比推錯好**。

這條 SHALL 寫進 spec 條文並註明理由，否則後續維護者會發現兩處行為不一致而「修正」它。

## 決策 5：四道相關性防線，由便宜到昂貴

1. **候選在搜尋階段就受限**：site filter + `is_allowed_url`。
2. **字面比對先於模型**：結果的標題或內文必須真的出現該藥名或成分，使用
   `DrugCatalogService` 既有的正規化規則，SHALL NOT 做模糊比對。該服務自己的註解已載明
   「藥名相似不代表成分相同，而這裡偽陽性的代價是⋯」——同一個理由在這裡更強。
3. **LLM 判定使用結構化輸出**：`{is_about_this_drug: bool, concern_kind: recall|safety|
   supply|education|none, summary: str}`。只有 `is_about_this_drug` 為真**且**
   `concern_kind` 不是 `none` 才進 Tier 1。
4. **時效門檻**：`published_at` 超過門檻天數不進 Tier 1；**抽不到日期者一律不進 Tier 1**。
   gov.tw 頁面的日期位置不一致，抽取可靠度未量測（Open Question 2），因此缺席時的預設
   必須是排除而非放行。

**輸出防線分兩層**：卡片文案 SHALL NOT 出現停藥、換藥、加減劑量的建議，固定行動呼籲為
「請與您的醫師或藥師確認」。prompt 講一次，**再加一道後置字串檢查**——prompt 可被繞過，
後置檢查不會。後置檢查命中時 SHALL 整則丟棄，SHALL NOT 嘗試改寫（改寫等於讓模型再賭
一次）。

## 決策 6：摘要一律中性第三人稱，個人化只存在於版面

`drug_news.summary` SHALL 以中性第三人稱撰寫（「食藥署公告某批號回收」），SHALL NOT 出現
「您正在服用的」這類第二人稱脈絡。個人化只放在 Tier 1 卡片的標題列與一行提示。

這樣**分享時只要不帶那兩行就達成零洩漏**，不需要為分享另存一份摘要，也不需要在分享路徑
上做文字改寫（改寫是又一次模型呼叫、又一個出錯的地方）。

## 決策 7：分享的收件人 SHALL NOT 走 `NOTIFICATION_POLICY`

`family_authorization_service.notification_recipients()` 回答的是「這位當事人出事時該通知
誰」，其 docstring 明載該表與 `PERMISSIONS` 刻意分離，因為「他可以隨時去看我的健康資料」
與「我出事時要通知他」是兩種不同的信任。

「我主動分享一則公開消息給他」是**第三種**信任，而且門檻最低——分享卡零洩漏，內容是任何
人都能在官網上看到的公開資訊。把它塞進 `NOTIFICATION_POLICY` 會讓兩種語意互相污染：日後
有人調整通報政策，會在毫無關聯的地方改變分享行為。

收件人為**族譜成員**。防洗版由 `(recipient_id, news_ref)` 唯一索引承擔——同一則消息對同一
位收件人只送一次，不論幾位家人都按了認同。另設分享者每日次數上限。

族譜為空時 SHALL 回覆提示並引導至邀請流程，SHALL NOT 靜默失敗。

## 決策 8：每人每日至多一則

某天若有多種藥同時有消息，只推相關度最高的，其餘留待隔天。連發多張「你的藥有問題」對
高齡使用者是恐慌而非資訊。

## 決策 9：Tier 2 選材必須先從 chunk 收斂回文章

`health_articles_chunks` 是**切片**collection，一篇文章對應多個 chunk。Tier 2 SHALL 先依
`url`（`url` 為空時依 `original_title`）收斂為文章再排序，SHALL NOT 直接把單一 chunk 當成
一則消息——chunk 是切出來的片段，單獨呈現常常是半句話。

## 決策 10：去重與原子搶佔共用同一個唯一索引

`medical_news_deliveries` 的 `(user_id, news_ref)` 唯一索引一物二用：既是「推過就不再推」的
去重，也是多實例下的推播權搶佔（insert 成功才推）。這是 `medication_repository.upsert_log`
已在使用的同一招，不發明新機制。

## 資料模型

```
drug_news
  drug_key        正規化的成分名或中文品名
  key_kind        ingredient | name_zh
  url             必填；無 url 的來源不得產生消息卡
  title / source_name / published_at
  summary         中性第三人稱摘要
  concern_kind    recall | safety | supply | education
  content_hash    跨 url 去重（同一則公告常有轉載）
  indexed_at
  索引：(drug_key, published_at desc)、url unique

medical_news_deliveries
  user_id / news_ref / tier / pushed_at
  shared_at / share_recipient_count
  唯一索引 (user_id, news_ref)

medical_news_shares
  recipient_id / news_ref / sharer_id / sent_at
  唯一索引 (recipient_id, news_ref)
```

`news_ref` 同時要能指向 `drug_news` 的文件與知識庫文章（Tier 2 沒有 `drug_news` 文件），
因此是 `{kind, id_or_url}` 的複合值而非單純 ObjectId。

## 錯誤處理

| 情境 | 行為 |
| --- | --- |
| 索引排程整輪失敗 | 推播照常使用既有索引；heartbeat 分別登記，故仍可觀測 |
| 單一藥品搜尋逾時 | 跳過該藥，不影響同輪其他藥 |
| LLM 判定失敗 | fail closed（決策 4） |
| 後置字串檢查命中 | 整則丟棄，不改寫 |
| Flex 超過 LINE 大小上限 | 比照 `rag-answer-card` 的處理：先截斷摘要，仍超過則退回純文字 |
| push 失敗 | 不重試、不補推。比照用藥提醒的 misfire grace：延遲後的推播已失去時效意義 |
| 使用者沒有任何用藥資料 | 直接走 Tier 2，不視為錯誤 |

## 已知風險與證據缺口

本節刻意列出**尚未量測**的項目，避免把假設當成結論。

1. **LINE 方案額度已查證，但本專案的實際用量未查證。**

   官方方案（2026-09-02 查於 tw.linebiz.com，2026-11-01 起免費則數維持不變）：

   | 方案 | 月費 | 每月免費則數 | 超出後 |
   | --- | --- | --- | --- |
   | 輕用量 | 0 | 200 | **不可加購** |
   | 中用量 | 800 | 3,000 | **不可加購** |
   | 高用量 | 1,200 | 6,000 | 可加購，0.2 元／則起 |

   計費規則：Reply API、一對一聊天、自動回應、歡迎訊息**不計費**；Push API 計費，
   依目標好友數計算。計算時區為 GMT+9，台灣時間 23:00 起送出者計入隔日。

   用藥提醒全部走 Push API。依 `medication-reminders` 的三階遞進時序推算，每位用藥者
   每月 90～270 則（三時段）或 120～360 則（含 bedtime 四時段）：

   | 方案 | 現況可支撐的用藥者數 | 加上本功能（+30 則／人／月） |
   | --- | --- | --- |
   | 輕用量 200 | 不到 1 位 | — |
   | 中用量 3,000 | 11～33 位 | 10～25 位 |
   | 高用量 6,000 | 22～66 位 | 20～50 位 |

   **仍未查證的是本專案目前使用哪個方案、以及實際用量。** 上表的分母是從 spec 時序
   推算，不是帳單數字。

   **相關的既有風險（不屬本功能，但在此記錄）**：中用量以下不可加購，額度耗盡時
   `push_flex` 只是回傳 `False` 並記一筆 log——heartbeat 仍正常、tick 仍執行，
   排程器外觀完全健康，只有使用者端安靜地收不到服藥提醒。目前沒有任何機制會讓這件事
   被發現。
2. **gov.tw 頁面的 `published_at` 抽取可靠度未量測。** 決策 5 的第 4 道防線因此採取
   「抽不到就排除」，方向安全，但可能導致 Tier 1 命中率遠低於預期。
3. **Tier 1 的實際命中率完全未知。** 沒有真實使用者的用藥分布資料，也沒有「多久會出現一
   則命中某個常見藥的官方消息」的量測。可能的結果是 Tier 1 幾乎不觸發，整個功能退化成
   Tier 2 電子報——那不是失敗，但與提案動機不符，上線後 SHALL 量測。
4. **相關性判定的偽陽性率未量測，且目前沒有對應的 golden set。** `evals/rag/golden.jsonl`
   量的是檢索命中與查核判定，量不到「這則消息是否真的在講這個藥」。建議比照該題庫另建
   小型判定題庫，但不在本次範圍。
5. **兩種卡片版面能否讓長輩分辨，未經真機驗證。**（Open Question 1）

## Open Questions

1. Tier 1／Tier 2 的版面差異需真機測試確認長輩能分辨；若不能，決策 1 的稀釋防線失效，
   需重新考慮是否維持每日必推。
2. `published_at` 抽取策略：先做啟發式抽取並量測缺席率，再決定門檻天數。
3. 是否在用藥提醒卡上加一個入口，把使用者帶到消息卡——零額外 push 且開啟率高，但用藥
   提醒卡實測已達 LINE 大小上限的 79%（見 `rag-answer-card` 的量測），空間是否足夠需先量。
