## Context

四個角色、三級資料分類、以及**與授權分離的通知政策**都已經存在（`app/models/family_authorization.py`）。本 change 幾乎不需要新的機制，主要是把既有的三塊接起來：許可證資料集裡沒被取用的兩個欄位、`DrugCatalogService`、以及 `NOTIFICATION_POLICY`。

既有通知政策：

```python
NOTIFICATION_POLICY = {
    "high_risk_drug_alert": frozenset({"GUARDIAN", "CAREGIVER"}),
}
```

該表的註解已經寫下了本 change 需要的推理：CAREGIVER 在資料上只有 SENSITIVE 讀取權，但現實中往往是唯一在場的人；排除他，通報就送給了三小時後才看手機的子女。這個判斷對成分重複同樣成立。

## Goals / Non-Goals

**Goals**
- 長輩加入一個與現有用藥成分重複的非處方藥時，本人與家人都知道。
- 通知內容的揭露程度受既有授權矩陣約束，不另立規則。
- 白名單的每一項都有可被審視的納入理由。

**Non-Goals**
- 不阻擋任何操作。
- 不做藥物交互作用判定。
- 不取代藥師。訊息用語 SHALL 引導使用者詢問藥師，SHALL NOT 給出劑量建議。

## Decisions

### 決策 1：以英文學名比對，不以中文品名

主成分略述欄位存的是英文學名，以 `;;` 分隔，94.4% 有值。普拿疼、斯斯、明通治痛丹的中文品名毫無交集，主成分都是 `ACETAMINOPHEN`。

比對前正規化：去除括號補述（`ACETAMINOPHEN (PARACETAMOL)`）、統一大寫、收斂連續空白。**不做模糊比對**——藥名相似不代表成分相同，模糊比對在這裡的偽陽性代價是「對沒有風險的組合發警報」，久了會讓人忽略真的警報。

### 決策 2：只比對白名單成分，不比對全部

實測非處方藥最常見的成分裡有 `RIBOFLAVIN`（1,369）、`ASCORBIC ACID`（1,004）、`NIACINAMIDE`（990）——維生素。兩種綜合感冒藥都含維生素 B2 是常態，報出來沒有臨床意義。

全成分比對會讓警報變成背景雜訊，而這個功能的價值完全建立在「發出來的每一則都值得看」。

初版白名單以「實測出現頻率高 × 已知會累加致害」選出，每一項在 `resources/otc_watch_ingredients.json` 中附納入理由。這是資料驅動的起點，不是藥理審查的結論——tasks 1 要求每一項寫下依據，日後可被質疑與修正。

### 決策 3：不推給 MEMBER

MEMBER 依授權矩陣只能讀 GENERAL（藥品名稱、時段），看不到 SENSITIVE（適應症）。他能收到的訊息只有「媽媽新增了某某藥」——沒有用途、沒有重複警示。

那是一則沒有行動價值的訊息。收多了會讓人靜音整個帳號，連帶把之後真正的警示一起淹掉。而 2026-08 才發生過空提醒卡把 LINE 月額度打爆的事故，推播成本是實際約束。

因此沿用既有的 `{GUARDIAN, CAREGIVER}`，**不改政策表**。

### 決策 4：未偵測到重複時仍通知家人，但內容分級

本 change 的核心是成分重複，但「長輩自己買藥吃」這件事本身家人也該知道。兩者的訊息強度不同：

| 情境 | 使用者本人 | GUARDIAN／CAREGIVER |
|---|---|---|
| 非處方藥 + 成分重複 | ⚠ 這兩種藥都含 X，一起吃可能過量，請先問藥師 | ⚠ 媽媽新增 A 藥，與現有 B 藥成分重複（X） |
| 非處方藥、無重複 | （不打擾） | 媽媽新增了 A 藥，用途：⋯ |
| 處方藥 | （不打擾） | （不通知） |

處方藥不通知，因為它經過醫師診斷與藥師調劑，已有專業把關；再通知一次只是噪音。這也讓通知量與風險成正比。

### 決策 5：偵測失敗一律靜默，對主流程 fail-open

比對失敗、藥證庫查無、成分欄位為空——任一情況都記 log 後結束，不通知、不影響掃描與加入提醒的主流程。這與 `SafetyAlertService` 現行的「對主流程 fail-open、對通報 fail-closed」一致。

使用者並沒有在等這個結果，一則「風險偵測失敗」只會造成困惑。

### 決策 6：log 不得帶藥名、成分與姓名

沿用 `SafetyAlertService` 的既有約束。用藥組合本身就是病史的強烈線索——「乙醯胺酚 + 抗凝血劑」幾乎等同揭露當事人有心血管疾病。

## Risks / Trade-offs

| 風險 | 影響 | 緩解 |
|---|---|---|
| 白名單漏了真正危險的成分 | 該報的沒報 | tasks 1 要求逐項寫下依據，可被審視補充；漏報不會比現況更差（現況是完全不報） |
| 白名單過寬 | 警報變雜訊，真的警報被忽略 | 決策 2 的「頻率 × 已知致害」雙條件；上線後以實際觸發率檢視 |
| 家人覺得被通知太多 | 靜音整個帳號 | 決策 4 的分級：處方藥不通知，無重複時只給家人一則低強度訊息 |
| 長輩覺得被監控 | 抗拒使用掃描功能 | 訊息用語以「讓家人幫你看一下」為框架，非「已回報」 |
| 成分正規化不足導致漏配 | 該報的沒報 | 決策 1 明訂不做模糊比對；正規化規則以實測樣本驗證，見 tasks 2 |

## Migration Plan

`resources/drug_catalog.json` 需重跑 `scripts/build_drug_catalog.py`（不帶 `--fetch-images`／`--fetch-indications`，因此不下載照片、不呼叫 LLM）。舊版 catalog 沒有新欄位時，`DrugCatalogService` SHALL 視為「無成分資料」而靜默跳過偵測——不得因為欄位缺席而拋錯，那會讓整個掃描流程掛掉。

`NotificationKind` 新增一個值不影響既有推播；`NOTIFICATION_POLICY` 若漏了新的 kind，`notification_recipient_roles` SHALL 回空集合而非拋錯，效果是「不通知任何人」——與決策 5 的 fail-closed 方向一致。
