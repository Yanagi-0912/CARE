### 現行實作落空的樣態

21 筆落空 + 1 筆比錯。落空的不是冷僻說法：

```
流鼻水、流鼻涕、鼻子一直流水、眼睛看東西模糊、眼睛有黑點在飄、
心情很低落、一直想尿尿、走路不太穩、手會抖、沒有食慾、體重一直掉、
脖子摸到腫塊、整天很累、最近一直頭暈、有點頭痛
```

比錯的一筆：`皮膚很癢` → `異位性皮膚炎`（應為 `皮膚癢`）。

跨語言 **6/6 全部落空**，因為 754 條別名全是 zh-TW。這不是覆蓋率低，是該語言下比對層等同不存在。

### 結論

手寫別名的問題不是「補得不夠」，是**沒有完成條件**：754 條別名撐出 48%，而漏掉的是「流鼻水」這種等級的說法。向量在零別名的前提下達到 86%，且跨語言直接可用。

**採用向量比對取代手寫別名。**

## 1.3 門檻校準（`SYMPTOM_MATCH_MIN_SCORE`）

### 決定性的一筆：top1 不可單獨採信

```
眼壓高    top1 = 高血壓 (0.942)    top2 = 青光眼 (0.897)    margin = 0.045
```

不是險勝，是有把握地錯，而且**跨科**——高血壓走內科（心臟），青光眼走眼科。
純採 top1 會把眼科病人送去心臟內科。

其餘 5 筆 top1 錯誤都是無害的近義擺盪（`流鼻水`→流鼻血 vs 鼻炎 margin 0.001；
`runny nose`→鼻過敏 vs 鼻炎 margin 0.001），只有這筆是真正危險的錯法。

### 但 top-3 涵蓋率是 100%

42 筆正樣本的正解**全部**落在前三名，含跨語言、含 `眼壓高`。

因此比對層的定位是**召回**，不是決選。決選仍交給現有的 enum LLM，
差別在候選集合從 391 條縮成 5–10 條。

補 `流鼻水` 的成因值得記下來：向量**有**召回（鼻炎 0.879、鼻過敏 0.880），
是 LLM 決選回了 UNKNOWN。因為表內鼻分泌物相關條目全是疾病名，而 `_classify`

就是診斷（決策 8）。

### 向量比對的已知邊界：詞面無關的專名同義詞

```
cos(皮蛇, 帶狀皰疹) = 0.817     ← 低於門檻，打「皮蛇」會落到保底
cos(皮蛇, 帶狀皰疹（皮蛇）) = 0.880  ← 併列後進得了決選
```

「皮蛇」是對外觀的比喻，與醫學名之間**沒有可推導的語意關係**，向量推不出來。
語意近似（肚子痛 ≈ 腹痛）向量可以處理，任意命名慣例（皮蛇 ≡ 帶狀皰疹）不行。

這類同義詞是**有限的封閉集合**（皮蛇、媽媽手、網球肘、鬼剃頭…），與已廢止的
開放集合別名表不同，處置方式為在 `term` 併列俗名——同表的 香港腳、富貴手、
五十肩、灰指甲 本來就是以俗名收錄。**尚未做系統性掃描**，應併入 tasks 1.2。

## 附帶發現

### 常見症候群的多症狀會自行落到合法條目

```
我咳嗽流鼻水  → 感冒     (0.934)
發燒又咳嗽    → 感冒發燒  (0.962)
頭痛又想吐    → 頭痛     (0.941)
```

落點都是表內既有條目，答案也合理。

### 但跨科並列仍需拆解

```
我青光眼又腸胃炎  → 腸胃炎 (0.908)  vs  青光眼 (0.906)   margin = 0.002
```

等同擲硬幣挑一個、丟掉另一個。向量比對解決不了跨科並列，
需要「先拆解症狀片語、再逐一比對」，屬另一階段工作。

### `task_type` 不可照抄 RAG

`app/dependencies.py:105-127` 刻意用非對稱配對（`RETRIEVAL_DOCUMENT` / `RETRIEVAL_QUERY`），
那是為「問句 → 文件段落」設計的。症狀比對是短語對短語、關係對稱，
應使用 `SEMANTIC_SIMILARITY`：前三名涵蓋率 100% vs 90%。

直接複用現成的 embeddings 實例會讓相似度分佈變差，且**壞得安靜**——
只會表現為門檻怎麼調都不對。

### 768 維足夠，且不需要 numpy

768 維與 3072 維同分（top1 36/42、top3 100%），記憶體 4.8 MB → 1.2 MB。

純 Python（`sum(map(mul, ...))`）比對 391 筆實測：

| 維度 | 耗時 |
|---|---|
| 768 | 4.6 ms |
| 1536 | 9.6 ms |
| 3072 | 18.3 ms |

**768 維下 4.6 ms，無須新增相依，也無須走 Atlas `$vectorSearch`。**
391 筆用 ANN 近似搜尋反而會讓門檻校準的數字不穩，且需在 Atlas 手動建第三個索引。

向量的儲存與查詢應分開看：Mongo（或檔案）負責持久化以免每次啟動重算，
查詢一律在記憶體做精確比對。存檔時 SHALL 一併存入對照表內容的 hash，
啟動時比對，不符即重算——否則 tasks 2.2 改寫 `term` 之後，
向量會**靜默**指向錯誤的條目。

## 重跑方式

一次性腳本，未進 repo。重跑時需重新撰寫，步驟為：

1. 以 `SEMANTIC_SIMILARITY` 對 391 條 `term` 與測試集取向量（`GoogleGenerativeAIEmbeddings`），存成 JSON
2. 正規化後取內積得 cosine 相似度，對每個查詢排序取 top-k，計算 top1／top3 命中與分數分佈
3. 現行實作的對照組直接呼叫 `SymptomNormalizer.resolve_from_table()`（不走 LLM）

取向量與分析必須分兩支：分析參數要反覆調整，重取向量會重複消耗 quota。
